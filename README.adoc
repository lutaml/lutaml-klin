== Purpose

Lutaml-Klin orchestrates UML-to-XSD transformation workflows using pre-built
LUR (LutaML UML Repository) and LXR (LutaML XSD Repository) packages for
optimal performance and reliability.

It provides a complete solution for:

* **Mapping generation**: Create YAML mappings showing UML class ↔ XSD element relationships
* **Type resolution**: Resolve UML types to XSD types using multiple strategies
* **Validation**: Generate comprehensive reports tracking resolution status
* **Interactive browsing**: Generate SPA websites for exploring mappings
* **Bidirectional lookup**: Query mappings in both directions (UML→XSD or XSD→UML)

The system is designed around pre-built packages that are created once and used
many times, eliminating the need for repeated parsing of large XMI and XSD files.

== Features

* <<lur-lxr-integration,LUR+LXR Package Integration>>: Fast loading from pre-built packages
* <<mapping-generation,UML-to-XSD Mapping>>: Comprehensive mapping with resolution tracking
* <<xsd-generation,XSD Schema Generation>>: Generate ShapeChange-compatible XSD schemas from UML with **100% rule parity** for PLATEAU URO/URF (37/37 conversion rules)
* <<type-resolution,Type Resolution Engine>>: Multi-strategy resolution (overrides, ShapeChange, schema repository)
* <<validation,Validation Reports>>: JSON and Markdown reports with statistics
* <<bidirectional-lookup,Bidirectional Lookup>>: Query mappings in both directions
* <<spa-generation,Interactive SPA Website>>: Browse mappings in a web interface
* <<unified-process,Unified Process Command>>: Single command for complete workflow
* <<cli-interface,CLI Interface>>: Thor-based command-line tools for all operations

== Architecture

Lutaml-Klin follows a clean 4-layer architecture with strict separation of concerns:

.High-level architecture with LUR+LXR integration
[source]
----
┌────────────────────────────────────────────────────────────┐
│  Input: Pre-built Packages (Built Once, Used Many Times)   │
│                                                             │
│  LUR Package (.lur)     LXR Package (.lxr)                 │
│  UML Model from XMI     XSD Schemas                        │
│  Built by: lutaml       Built by: lutaml-xsd               │
│  Load time: <100ms      Load time: <100ms                  │
└────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────────┐
│  lutaml-klin: Pure Orchestration (No Parsing!)             │
│                                                             │
│  1. Load LUR → UmlRepository API                           │
│  2. Load LXR → SchemaRepository API                        │
│  3. Load ShapeChange Config                                │
│  4. Execute Resolution (Strategy Pattern)                  │
│  5. Generate Outputs (YAML, Reports, SPA)                  │
└────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────────┐
│  Output: Three Formats                                      │
│                                                             │
│  ├─ YAML Mappings (per package)                            │
│  ├─ Validation Reports (JSON/Markdown)                     │
│  └─ SPA Website (Interactive HTML/JS)                      │
└────────────────────────────────────────────────────────────┘
----

----

        │               │               │
        ▼               ▼               ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐

│  (Priority 1)│ │  (Priority 2)│ │  Strategy    │
│              │ │              │ │  (Priority 3)│
└──────────────┘ └──────────────┘ └──────────────┘
     │                  │                  │

[[shapechange-process]]
== ShapeChange Integration

=== General

Lutaml-klin integrates with ShapeChange by using ShapeChange XML configuration
files to drive the mapping process. This provides compatibility with existing
ShapeChange-based workflows while offering significant performance improvements.

=== How It Works

Lutaml-klin uses ShapeChange configurations in three ways:

1. **For Mapping Documentation** (`process` command): Extract encoding rules and
   type mappings to document how UML maps to existing XSD schemas

2. **For XSD Generation** (`xsd` command): Apply encoding rules to generate new
   XSD schemas from UML models

3. **For Automatic LXR Creation** (`--auto-lxr` flag): Extract schema locations
   from config to automatically build LXR packages

.ShapeChange configuration usage workflow
[source]
----
ShapeChange Config XML
       │
       ├─ Package Information
       │  └─→ Maps UML packages to XSD namespaces
       │
       ├─ Type Mappings (xsdMapEntries)
       │  └─→ Defines UML type → XSD type rules
       │
       ├─ Encoding Rules
       │  └─→ Transformation rules for XSD generation
       │
       └─ Namespace Declarations
          └─→ XML namespace prefix → URI mappings
----

=== Running ShapeChange-Compatible Workflows

==== Complete PLATEAU Mapping Workflow

[example]
====
[source,shell]
----
# Step 1: Build LUR package from PLATEAU XMI (one-time)
lutaml xmi package build \
  /path/to/plateau/20251010-242.xmi \
  -o packages/plateau_all.lur

# Step 2: Process with ShapeChange config using auto-LXR
# This automatically extracts schema info from config and creates LXR
lutaml-klin process \
  --lur packages/plateau_all.lur \
  --shapechange reference/shapechange-configs/ShapeChangeConfig_Plateau_urf.xml \
  --auto-lxr \
  --packages "**::urf,**::uro" \
  --output plateau_output/ \
  --verbose

# Step 3: Query the generated mappings
lutaml-klin lookup "UrbanPlanningArea" \
  --mapping plateau_output/mappings/schema_mapping.yaml

# Step 4: Browse interactive SPA
open plateau_output/spa/index.html
----

This workflow:

* Uses ShapeChange config to extract schema locations
* Automatically creates cached LXR package
* Applies ShapeChange encoding rules for type resolution
* Generates complete documentation with traceability

The `--auto-lxr` flag means you don't need to manually create the LXR package—
lutaml-klin extracts schema information from the ShapeChange config and builds
it automatically with intelligent caching.
====

==== Manual LXR Package Creation

If you prefer to create and reuse LXR packages manually:

[example]
====
[source,shell]
----
# Step 1: Extract schema info from ShapeChange config
lutaml-klin create-lxr \
  --shapechange reference/shapechange-configs/ShapeChangeConfig_Plateau_urf.xml \
  --output packages/plateau_schemas.lxr \
  --name "PLATEAU Schemas" \
  --version "3.2" \
  --validate

# Step 2: Use the LXR package for processing
lutaml-klin process \
  --lur packages/plateau_all.lur \
  --lxr packages/plateau_schemas.lxr \
  --config reference/shapechange-configs/ShapeChangeConfig_Plateau_urf.xml \
  --packages "**" \
  --output output/
----

The LXR package can be reused across multiple runs and projects, loading in
<100ms vs seconds for XSD parsing.
====

=== ShapeChange Config Features Supported

✅ **XsdMapEntry**: Type mappings with encoding rule filters
✅ **XmlNamespace**: Namespace prefix and URI declarations
✅ **PackageInfo**: Package-to-namespace mappings
✅ **EncodingRule**: Rule inheritance and composition
✅ **XInclude**: Modular configuration files
✅ **Target parameters**: Output directory, encoding rule defaults

Not yet supported (future enhancements):
- Some advanced transformation rules
- Constraint mapping
- Profile-based filtering

== Installation

Add this line to your application's Gemfile:

[source,ruby]
----
gem "lutaml-klin"
gem "lutaml", "~> 1.0"      # For LUR packages
gem "lutaml-xsd", "~> 1.0"  # For LXR packages
----

And then execute:

[source,shell]
----
bundle install
----

Or install it yourself as:

[source,shell]
----
gem install lutaml-klin
gem install lutaml lutaml-xsd
----

[[quick-start]]
== Quick Start

=== General

The fastest way to get started is using the unified `process` command that
handles the complete workflow in a single operation.

=== Prerequisites

Before running lutaml-klin, you need to build LUR and LXR packages from your
source files:

[source,shell]
----
# 1. Build LUR package from XMI (one-time operation)
lutaml xmi package build model.xmi -o model.lur

# 2. Build LXR package from XSD schemas (one-time operation)
lutaml-xsd package build config.yaml -o schemas.lxr
----

=== Complete Workflow

[source,shell]
----
# 3. Generate mappings, validation, and SPA website
lutaml-klin process \
  --lur model.lur \
  --lxr schemas.lxr \
  --config shapechange.xml \
  --packages "**" \
  --output output/
----

This single command will:

* Load the UML model from the LUR package
* Load the XSD schemas from the LXR package
* Parse the ShapeChange configuration
* Generate YAML mappings for all packages
* Create validation reports (JSON and Markdown)
* Generate an interactive SPA website

.Output directory structure
====
[source]
----
output/
├── mappings/
│   ├── ModelRoot_Core.yaml
│   ├── ModelRoot_Extensions.yaml
│   └── ...
├── validation/
│   ├── validation_report.json
│   └── validation_report.md
└── spa/
    ├── index.html
    ├── assets/
    │   ├── css/
    │   └── js/
    └── data/
        └── mappings.json
----
====

[[unified-process]]
=== Process Command (Unified Workflow)

==== General

The `process` command is the recommended way to use lutaml-klin. It executes
the complete UML-to-XSD mapping workflow in a single operation.

==== Syntax

[source,shell]
----
lutaml-klin process \
  --lur PATH \
  --lxr PATH \
  --config PATH \
  --packages PATTERN \
  --output PATH \
  [--type-overrides PATH] \
  [--generate-mappings] \
  [--generate-spa] \
  [--validate] \
  [--verbose]
----

Where,

`--lur PATH`:: Path to the LUR package file (.lur)
`--lxr PATH`:: Path to the LXR package file (.lxr)
`--config PATH`:: Path to the ShapeChange configuration XML file
`--packages PATTERN`:: Package filter pattern (e.g., "i-UR::**", default: "**")
`--output PATH`:: Output directory path
`--type-overrides PATH`:: Optional path to type override YAML file
`--generate-mappings`:: Generate YAML mappings (default: true)
`--generate-spa`:: Generate SPA website (default: true)
`--validate`:: Generate validation reports (default: true)
`--verbose`:: Enable detailed logging

==== Example: Full workflow for PLATEAU URF package

[example]
====
[source,shell]
----
lutaml-klin process \
  --lur plateau_uml.lur \
  --lxr plateau_schemas.lxr \
  --config reference/shapechange-configs/ShapeChangeConfig_Plateau_urf.xml \
  --packages "ModelRoot::i-UR::**" \
  --output output/ \
  --verbose
----

This generates:

* YAML mappings for all packages matching the filter
* JSON validation report with statistics
* Markdown validation report for human review
* Interactive SPA website for browsing mappings
====

==== Example: With type overrides

[example]
====
Create a type override file `overrides.yaml`:

[source,yaml]
----
type_overrides:
  OldTypeName: NewTypeName
  CharacterString: string
  Integer: integer
----

Then run:

[source,shell]
----
lutaml-klin process \
  --lur model.lur \
  --lxr schemas.lxr \
  --config config.xml \
  --packages "**" \
  --output output/ \
  --type-overrides overrides.yaml
----
====

==== Example: Mappings only (skip validation and SPA)

[example]
====
[source,shell]
----
lutaml-klin process \
  --lur model.lur \
  --lxr schemas.lxr \
  --config config.xml \
  --packages "**" \
  --output output/ \
  --no-validate \
  --no-generate-spa
----
====

[[bidirectional-lookup]]
=== Lookup Commands

==== General

The lookup commands provide bidirectional query capabilities for exploring
mappings.

==== Auto-detection Lookup

The `lookup` command auto-detects the lookup direction based on the identifier
format.

[source,shell]
----
lutaml-klin lookup IDENTIFIER \
  --mapping PATH \
  [--format text|json|yaml] \
  [--fuzzy] \
  [--verbose]
----

Where,

`IDENTIFIER`:: UML class/attribute name or XSD type/element name
`--mapping PATH`:: Path to mapping YAML file
`--format FORMAT`:: Output format (text, json, or yaml; default: text)
`--fuzzy`:: Enable fuzzy matching
`--verbose`:: Enable detailed logging

.Example: Lookup UML class
[example]
====
[source,shell]
----
lutaml-klin lookup "ModelRoot::i-UR::urf::UrbanPlanningArea" \
  --mapping output/mappings/ModelRoot_i-UR_urf.yaml
----

Output:
[source,text]
----

[[ruby-api]]
== Ruby API

=== General

Lutaml-Klin provides a comprehensive Ruby API for programmatic usage.

=== Mapping Generation

.Basic mapping workflow
[example]
====
[source,ruby]
----
require 'lutaml/klin'

# Initialize repositories
uml_repo = Lutaml::Klin::Repositories::UmlRepositoryAdapter.new(
  lur_path: "model.lur"
)
xsd_repo = Lutaml::Klin::Repositories::SchemaRepositoryAdapter.new(
  lxr_path: "schemas.lxr"
)

# Load ShapeChange configuration
config = Lutaml::Klin::ShapeChange::ConfigParser.parse_file(
  "shapechange.xml"
)

# Create mapping workflow
workflow = Lutaml::Klin::Application::MappingWorkflow.new(
  uml_repository: uml_repo,
  xsd_repository: xsd_repo,
  shapechange_config: config,
  type_overrides: {"OldType" => "NewType"}
)

# Generate mapping for a package
mapping = workflow.generate_mapping_for_package("ModelRoot::Core")

# Save to file
workflow.save_mapping(mapping, "output/core_mapping.yaml")
----
====

.Multiple packages
[example]
====
[source,ruby]
----
# Generate mappings for multiple packages
packages = ["ModelRoot::Core", "ModelRoot::Extensions"]
schema_mapping = workflow.generate_mappings_for_packages(packages)

# Access mapping data
schema_mapping.package_mappings.each do |pkg_mapping|
  puts "Package: #{pkg_mapping.uml_package_name}"
  puts "Resolution rate: #{pkg_mapping.resolution_rate}%"

  pkg_mapping.class_mappings.each do |class_mapping|
    puts "  Class: #{class_mapping.uml_name}"
    puts "  XSD Type: #{class_mapping.xsd_type_name}"
    puts "  Status: #{class_mapping.resolution_status}"
  end
end
----
====

=== Validation Workflow

.Generate validation reports
[example]
====
[source,ruby]
----
require 'lutaml/klin'

# Load existing mapping
mapping = Lutaml::Klin::Mapping::SchemaMapping.from_yaml(
  File.read("output/mappings/complete.yaml")
)

# Create validation workflow
validation = Lutaml::Klin::Application::ValidationWorkflow.new

# Generate reports
result = validation.validate_and_report(mapping, "output/validation/")

# Access validation results
puts "Total classes: #{result.statistics[:total_classes]}"
puts "Resolved: #{result.statistics[:resolved_classes]}"
puts "Resolution rate: #{result.statistics[:resolution_rate]}%"

# Check specific issues
result.issues.each do |issue|
  puts "#{issue[:severity]}: #{issue[:message]}"
end
----
====

=== Lookup Workflow

.Programmatic lookups
[example]
====
[source,ruby]
----
require 'lutaml/klin'

# Initialize lookup workflow
lookup = Lutaml::Klin::Application::LookupWorkflow.new(
  "output/mappings/complete.yaml"
)

# UML to XSD lookup
result = lookup.lookup_uml_to_xsd(
  "ModelRoot::i-UR::urf::UrbanPlanningArea"
)

if result.found?
  result.matches.each do |match|
    puts "UML: #{match[:uml_class]}"
    puts "XSD: #{match[:xsd_type]}"
    puts "Namespace: #{match[:xsd_namespace]}"
  end
end

# XSD to UML lookup
result = lookup.lookup_xsd_to_uml("gml:CodeType", fuzzy: true)

# Format result as JSON
json_output = lookup.format_result(result, format: :json)
puts json_output
----
====

[[type-resolution]]
== Type Resolution

=== General

The Resolution Engine uses a strategy pattern with three ordered strategies:

1. **Type Override Strategy**: User-defined type mappings (highest priority)
2. **ShapeChange Mapping Strategy**: Mappings from ShapeChange configuration
3. **Schema Repository Strategy**: Direct XSD schema lookups (lowest priority)

=== Resolution Result

Each resolution produces a result with:

* **Status**: `resolved`, `partial`, or `unresolved`
* **Method**: Which strategy resolved the type
* **Confidence**: Confidence score (0.0 to 1.0)
* **Metadata**: Additional resolution details
* **Error**: Error message if unresolved

=== Example Resolution Flow

[source]
----
UML Type: "CharacterString"
     │
     ▼
1. Type Override Strategy
   Check: type_overrides["CharacterString"]
   Result: "string" ✓ (confidence: 1.0)

   → Resolution complete, skip remaining strategies
----

[[xsd-generation]]
== XSD Schema Generation

=== General

Lutaml-Klin provides complete XSD schema generation from UML models, offering a
pure Ruby alternative to ShapeChange. The implementation follows ShapeChange's
encoding rules and generates identical XSD output.

=== Features

* **ShapeChange compatibility**: Generates XSD schemas matching ShapeChange output
* **Rule-based processing**: Implements standard ShapeChange encoding rules
* **Multiple processors**: Object elements, complex types, sequences, property types, enumerations, code lists
* **Configurable**: Uses ShapeChange XML configuration files
* **Package-based**: Generate schemas for specific packages or all packages

=== Architecture

.XSD Generation workflow
[source]
----
┌─────────────────────────────────────────────────────────┐
│  Input: UML Model + ShapeChange Configuration           │
│                                                          │
│  LUR Package (.lur)     ShapeChange Config (.xml)       │
│  UML Classes, Enums     Encoding Rules, Map Entries     │
└─────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────┐
│  XSD Generator (Rule-Based Processor Chain)             │
│                                                          │
│  1. Load encoding rules from config                     │
│  2. Select packages to process                          │
│  3. Apply processors to each class:                     │
│     • ObjectElementProcessor    → <xs:element>          │
│     • ComplexTypeProcessor      → <xs:complexType>      │
│     • SequenceProcessor         → <xs:sequence>         │
│     • PropertyElementProcessor  → property elements     │
│     • PropertyTypeProcessor     → property types        │
│     • EnumerationProcessor      → <xs:simpleType>       │
│     • CodeListProcessor         → code list types       │
│  4. Generate XSD document with namespaces               │
└─────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────┐
│  Output: XSD Schema Files                               │
│                                                          │
│  ├─ urbanObject.xsd (URO package)                       │
│  ├─ urbanFunction.xsd (URF package)                     │
│  └─ ... (one file per package)                          │
└─────────────────────────────────────────────────────────┘
----

=== Encoding Rules

The XSD generator implements ShapeChange encoding rules:

* `rule-xsd-cls-object-element`: Generate global element for each class
* `rule-xsd-cls-type`: Generate complex type for each class
* `rule-xsd-cls-sequence`: Generate xs:sequence for properties
* `rule-xsd-prop-element`: Generate property elements
* `rule-xsd-prop-propertyType`: Generate property type wrappers
* `rule-xsd-cls-enum-object-element`: Generate enumeration types
* `rule-xsd-cls-codelist-object-element`: Generate code list types

These rules are configured in the ShapeChange XML configuration file.

* XML Schema specification compliance
* GML/ISO 19136 conventions

=== Anonymous Property Type Patterns

Lutaml-Klin generates three types of anonymous property types based on encoding requirements, matching ShapeChange's behavior:

==== Pattern A: By-Reference Encoding

Used when `inlineOrByReference="byreference"` or for code lists encoded as dictionaries.

.Anonymous type with gml:ReferenceType
[example]
====
[source,xml]
----
<element name="relatedBuilding">
  <complexType>
    <complexContent>
      <extension base="gml:ReferenceType">
        <attribute name="nilReason" type="gml:NilReasonType"/>
      </extension>
    </complexContent>
  </complexType>
</element>
----
====

==== Pattern B: Inline Encoding

Used when `inlineOrByReference="inline"` for embedded content only.

.Anonymous type with direct element reference
[example]
====
[source,xml]
----
<element name="component">
  <complexType>
    <sequence minOccurs="0">
      <element ref="uro:Building"/>
    </sequence>
  </complexType>
</element>
----
====

==== Pattern C: Standard InlineOrByReference

Default pattern supporting both inline and by-reference via xlink:href.

.Anonymous type with full associations
[example]
====
[source,xml]
----
<element name="building">
  <complexType>
    <sequence minOccurs="0">
      <element ref="uro:Building"/>
    </sequence>
    <attributeGroup ref="gml:AssociationAttributeGroup"/>
    <attributeGroup ref="gml:OwnershipAttributeGroup"/>
  </complexType>
</element>
----

For properties requiring special attributes (`nilReason`, `metadata`, `qualifiers`), an anonymous type is generated instead of using the standard PropertyType.
