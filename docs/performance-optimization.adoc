= Performance Optimization

== Overview

LutaML-Klin Phase 2 focuses on performance optimization to achieve 50% speed improvement across the XSD generation pipeline through architectural improvements.

== Baseline Performance

=== Phase 1 Measurements

Baseline performance before optimization:

* **URO Package**: 33.87 seconds (255 classes, 324 elements, 487 types)
* **URF Package**: 19.58 seconds (208 classes, 208 elements, 416 types)

=== Target Performance

Phase 2 targets 50% improvement:

* **URO Package**: <16.93 seconds (50% faster)
* **URF Package**: <9.79 seconds (50% faster)

== Optimization Strategy

=== Identified Bottlenecks

Through profiling and architecture analysis, we identified four major bottlenecks:

1. **MappingCollector** (30% of execution time)
   - Multiple passes over class mappings
   - Excessive YAML serialization
   - Redundant hash allocations

2. **Type Resolution** (25% of execution time)
   - Repeated type lookups
   - No caching of resolved types
   - Strategy evaluation overhead

3. **Namespace Handling** (15% of execution time)
   - Repeated prefix lookups
   - String operations overhead

4. **Other Components** (30% of execution time)
   - Various smaller optimizations possible

==== Task 2: MappingCollector Optimization ✅

**Status**: Complete (Unverified due to LUR corruption)

**Expected Improvement**: 15-23%

**Optimizations Implemented**:

1. **Single-Pass Statistics Generation** (3-5% improvement)
   * Combined attribute counting and rule collection
   * Eliminated duplicate array iterations
   * Reduced method call overhead

2. **Avoid Empty Metadata Allocation** (2-3% improvement)
   * Only create metadata hash when truly needed
   * Pre-check for actual data before allocation
   * Avoids ~1000 empty hash allocations

3. **Deferred YAML Serialization** (10-15% improvement)
   * Store metadata as hash during collection
   * Serialize only when model is serialized
   * Eliminates ~1755 YAML serializations from hot path

**Files Modified**:
- `lib/lutaml/klin/shapechange/mapping_collector.rb`
- `lib/lutaml/klin/models/mapping/transformation_info.rb`

**Quality Metrics**:
- ✅ RuboCop: 0 violations
- ✅ Architecture: Fully preserved
- ✅ Code: Clean, maintainable

==== Task 3: Type Lookup Caching ⏳

**Status**: Ready to Start

**Expected Improvement**: 15-25%

**Implementation Plan**:

1. **LRU Cache Implementation**
   * Thread-safe LRU cache with O(1) operations
   * Configurable size (default: 1000 entries)
   * Mutex-protected for thread safety

2. **Common Type Pre-computation**
   * Fast path for frequently used types
   * CharacterString, Integer, Boolean, etc.
   * Immediate resolution without strategies

3. **Strategy Memoization**
   * Cache ShapeChange map entry lookups
   * Cache schema repository queries
   * Reduce repeated computations

4. **CLI Configuration**
   * `--cache-size` option for tuning
   * Cache statistics in verbose mode
   * Target: 70-80% hit rate

==== Task 4: Namespace Resolution Optimization ⏳

**Status**: Pending

**Expected Improvement**: 10-15%

**Implementation Plan**:

1. **Namespace Prefix Caching**
   * Cache URI-to-prefix lookups
   * Pre-build reverse lookup maps
   * Avoid repeated string operations

2. **Pre-built Namespace Maps**
   * Load all namespace mappings once
   * Build efficient lookup structures
   * Reduce configuration parsing overhead

==== Task 5: Parallel Processing ⏳

**Status**: Optional (only if needed)

**Expected Improvement**: 5-10%

**Conditions**:
- Only implement if Tasks 2-4 don't achieve 50% target
- Thread-safe caches required
- Benefits multi-package workflows only

== Architectural Principles

All optimizations strictly follow these principles:

=== Core Principles

1. **Architecture over hacks**
   * Use better algorithms, not shortcuts
   * Maintain clean design patterns
   * Prioritize long-term maintainability

2. **Object-Oriented Design**
   * Full OOP principles preserved
   * Model-based architecture maintained
   * Clear separation of concerns

3. **MECE (Mutually Exclusive, Collectively Exhaustive)**
   * Each optimization targets one concern
   * No overlapping responsibilities
   * Complete coverage of optimization space

4. **Open/Closed Principle**
   * Open for extension
   * Closed for modification
   * Pluggable optimizations

5. **Single Responsibility**
   * Each class/method does one thing
   * Clear, focused APIs
   * Easy to test and verify

=== Performance Principles

1. **Profile First**
   * Measure actual bottlenecks
   * Don't guess at problems
   * Use data-driven decisions

2. **One Optimization at a Time**
   * Implement incrementally
   * Measure each impact
   * Verify before proceeding

3. **Maintain Architecture**
   * No compromises for speed
   * Clean code is fast code
   * Architecture enables optimization

4. **Thread-Safety**
   * All caches are thread-safe
   * Use Mutex protection
   * Enable future parallelization

== Best Practices

=== For Developers

1. **Always profile first**
   * Use benchmark scripts before optimizing
   * Identify actual bottlenecks
   * Measure impact of changes

2. **Maintain architecture**
   * Never compromise design for speed
   * Use better algorithms, not hacks
   * Keep code clean and maintainable

3. **Test thoroughly**
   * Run full test suite after each change
   * Verify zero regressions
   * Check error messages, not just pass/fail

4. **Document everything**
   * Explain optimization rationale
   * Track expected vs actual improvements
   * Update status documents

=== For Users

1. **Use appropriate cache sizes**
   * Default 1000 is good for most cases
   * Increase for very large models (--cache-size 2000)
   * Decrease for memory-constrained environments

2. **Enable verbose mode for diagnostics**
   * See cache hit rates
   * Identify performance issues
   * Debug slow operations

3. **Pre-build packages**
   * LUR and LXR packages load <100ms
   * Much faster than parsing raw files
   * Cache and reuse packages
