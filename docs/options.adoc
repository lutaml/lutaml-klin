= Configuration Options

== Purpose

This document provides a comprehensive reference for all configuration options
available in Lutaml-Klin.

Use this guide to:

* Understand all command-line options
* Configure ShapeChange integration settings
* Customize mapping generation behavior
* Set up environment variables for automation

== Concepts

=== Option precedence

When the same option is specified in multiple places, this precedence order
applies (highest to lowest):

1. Command-line flags (e.g., `--verbose`)
2. Environment variables (e.g., `LUTAML_KLIN_VERBOSE=1`)
3. Configuration files (future feature)
4. Default values

=== Option types

Options are categorized as:

* **Required**: Must be provided for command to execute
* **Optional**: Have default values, can be overridden
* **Global**: Available for all commands
* **Command-specific**: Only for specific commands

== Global options

These options work with all commands.

=== --version

Display the Lutaml-Klin version number.

**Type:** Global, optional

**Default:** N/A

**Example:**

[source,shell]
----
lutaml-klin --version
# Output: Lutaml-Klin version 0.1.0
----

=== --help, -h

Display help information for commands.

**Type:** Global, optional

**Default:** N/A

**Usage:**

[source,shell]
----
# General help
lutaml-klin --help
lutaml-klin help

# Command-specific help
lutaml-klin generate --help
lutaml-klin help generate
----

=== --verbose, -v

Enable detailed logging output.

**Type:** Global, optional

**Default:** `false`

**Environment variable:** `LUTAML_KLIN_VERBOSE=1`

**Example:**

[source,shell]
----
lutaml-klin generate \
  --xmi model.xmi \
  --config config.xml \
  --output map.yaml \
  --verbose
----

**Verbose output includes:**

* File parsing progress
* Package and class counts
* Type mapping discoveries
* Processing steps
* Success/error messages with context

== Generate command options

=== --xmi PATH

Path to the UML model in XMI format.

**Type:** Required

**Format:** File path (absolute or relative)

**Constraints:**

* File must exist and be readable
* Must be valid XML
* Should conform to XMI 2.x specification

**Example:**

[source,shell]
----
--xmi models/urban-planning.xmi
--xmi /absolute/path/to/plateau-uro.xmi
----

=== --config PATH

Path to the ShapeChange XML configuration file.

**Type:** Required

**Format:** File path (absolute or relative)

**Constraints:**

* File must exist and be readable
* Must be valid XML
* Should contain at minimum:
  - Input configuration
  - At least one target configuration
  - Encoding rules or type mappings

**Example:**

[source,shell]
----
--config config/shapechange-config.xml
--config reference/shapechange-configs/ShapeChangeConfig_Plateau_urf.xml
----

**Configuration structure:**

[source,xml]
----
<ShapeChangeConfiguration>
  <input id="...">
    <!-- Input configuration -->
  </input>
  <targets>
    <TargetXmlSchema ...>
      <!-- Target configuration with encoding rules -->
    </TargetXmlSchema>
  </targets>
</ShapeChangeConfiguration>
----

=== --output PATH

Path where the generated YAML mapping file will be written.

**Type:** Required

**Format:** File path (absolute or relative)

**Constraints:**

* Parent directory must be writable (or will be created)
* If file exists, it will be overwritten

**Example:**

[source,shell]
----
--output mappings/urban-planning.yaml
--output /absolute/path/to/output.yaml
----

**Output format:** YAML (SchemaMapping structure)

=== --xsd PATH

Path to XSD schema directory for type resolution (experimental).

**Type:** Optional

**Format:** Directory path (absolute or relative)

**Default:** `nil` (no XSD resolution)

**Constraints:**

* Directory must exist and be readable
* Directory should contain .xsd files
* XSD files should match namespaces in configuration

**Example:**

[source,shell]
----
--xsd schemas/
--xsd /path/to/xsd/schemas/
----

**Behavior:**

* When provided: Attempts to resolve namespaced types (e.g., `gml:CodeType`)
* When omitted: Types remain as-is from UML model

NOTE: Full XSD resolution requires integration with `lutaml-xsd` gem (planned).

== Report command options

=== --mapping PATH

Path to a YAML mapping file to generate report from.

**Type:** Required

**Format:** File path (absolute or relative)

**Constraints:**

* File must exist and be readable
* Must be valid YAML
* Must conform to SchemaMapping structure
* Typically generated by `generate` command

**Example:**

[source,shell]
----
--mapping mappings/urban-planning.yaml
--mapping plateau_mappings/uro.yaml
----

=== --output PATH

Path where the text report will be written.

**Type:** Required

**Format:** File path (absolute or relative)

**Constraints:**

* Parent directory must be writable
* If file exists, it will be overwritten

**Example:**

[source,shell]
----
--output reports/urban-planning-report.txt
--output uro-investigation.txt
----

**Output format:** Plain text with structured sections

== Merge command options

=== --inputs PATH1,PATH2,...

Comma-separated list of YAML mapping files to merge.

**Type:** Required

**Format:** Comma-separated file paths (no spaces)

**Constraints:**

* All files must exist and be readable
* All files must be valid YAML
* All files must conform to SchemaMapping structure
* At least one file must be specified

**Example:**

[source,shell]
----
--inputs map1.yaml,map2.yaml
--inputs mappings/uro.yaml,mappings/bldg.yaml,mappings/tran.yaml
----

**Merge behavior:**

* All package_mappings from all files are combined
* Encoding rules are deduplicated (first occurrence kept)
* No namespace conflict resolution (packages kept separate)

=== --output PATH

Path where the merged YAML file will be written.

**Type:** Required

**Format:** File path (absolute or relative)

**Constraints:**

* Parent directory must be writable
* If file exists, it will be overwritten

**Example:**

[source,shell]
----
--output mappings/combined.yaml
--output complete-plateau.yaml
----

== Validate command options

=== --mapping PATH

Path to a YAML mapping file to validate.

**Type:** Required

**Format:** File path (absolute or relative)

**Constraints:**

* File must exist and be readable
* Must be valid YAML
* Must conform to SchemaMapping structure

**Example:**

[source,shell]
----
--mapping mappings/uro.yaml
----

=== --xsd PATH

Path to the XSD schema directory.

**Type:** Required

**Format:** Directory path (absolute or relative)

**Constraints:**

* Directory must exist and be readable
* Directory should contain .xsd files matching the mapping

**Example:**

[source,shell]
----
--xsd schemas/uro/
--xsd /path/to/xsd/schemas/
----

**Validation checks:**

* Mapping completeness (all classes mapped)
* Type conversion correctness
* Multiplicity preservation
* Namespace consistency

== Environment variables

=== LUTAML_KLIN_VERBOSE

Enable verbose output for all commands.

**Type:** Boolean (0 or 1)

**Default:** `0` (disabled)

**Example:**

[source,shell]
----
export LUTAML_KLIN_VERBOSE=1
lutaml-klin generate --xmi model.xmi --config config.xml --output map.yaml
----

**Equivalent to:** Adding `--verbose` flag to every command

=== LUTAML_KLIN_LOG_LEVEL

Set the logging level.

**Type:** String (debug, info, warn, error)

**Default:** `info`

**Example:**

[source,shell]
----
export LUTAML_KLIN_LOG_LEVEL=debug
lutaml-klin generate --xmi model.xmi --config config.xml --output map.yaml
----

**Log levels:**

* `debug`: All messages including debug information
* `info`: Informational messages and above
* `warn`: Warnings and errors only
* `error`: Errors only

=== LUTAML_KLIN_CONFIG

Path to default configuration file (future feature).

**Type:** File path

**Default:** None

**Example:**

[source,shell]
----
export LUTAML_KLIN_CONFIG=~/.lutaml-klin/config.yaml
----

NOTE: This feature is planned for future releases.

== ShapeChange configuration options

These options are specified in the ShapeChange XML configuration file, not
on the command line.

=== Encoding rules

Define transformation patterns for UML-to-XSD conversion.

**Location:** `<TargetXmlSchema>` → `<rules>` → `<EncodingRule>`

**Example:**

[source,xml]
----
<TargetXmlSchema ...>
  <rules>
    <EncodingRule name="iso19136_2007_ShapeChange_1_0_0"
                  extends="iso19136_2007"/>
  </rules>
</TargetXmlSchema>
----

**Common encoding rules:**

* `iso19136_2007`: Base GML 3.2 encoding
* `iso19136_2007_ShapeChange_1_0_0`: Extended GML encoding
* Custom rules can extend base rules

=== Type mappings

Define UML type to XSD type conversions.

**Location:** `<TargetXmlSchema>` → `<xsdMapEntries>` → `<XsdMapEntry>`

**Example:**

[source,xml]
----
<xsdMapEntries>
  <XsdMapEntry>
    <type>CharacterString</type>
    <xmlType>string</xmlType>
    <xmlTypeNs>http://www.w3.org/2001/XMLSchema</xmlTypeNs>
  </XsdMapEntry>
  <XsdMapEntry>
    <type>Integer</type>
    <xmlType>integer</xmlType>
    <xmlTypeNs>http://www.w3.org/2001/XMLSchema</xmlTypeNs>
  </XsdMapEntry>
</xsdMapEntries>
----

**Fields:**

* `type`: UML type name
* `xmlType`: XSD type name
* `xmlTypeNs`: XSD type namespace
* `xmlElement` (optional): Element name if different from type

=== XML namespaces

Define namespace prefixes and schema locations.

**Location:** `<xmlNamespaces>` → `<XmlNamespace>`

**Example:**

[source,xml]
----
<xmlNamespaces>
  <XmlNamespace nsabr="gml"
                ns="http://www.opengis.net/gml/3.2"
                location="http://schemas.opengis.net/gml/3.2.1/gml.xsd"/>
  <XmlNamespace nsabr="xs"
                ns="http://www.w3.org/2001/XMLSchema"
                location="http://www.w3.org/2001/XMLSchema.xsd"/>
</xmlNamespaces>
----

**Fields:**

* `nsabr`: Namespace prefix (abbreviation)
* `ns`: Namespace URI
* `location`: Schema file location (URL or file path)

=== Package information

Define package-specific settings.

**Location:** `<packageInfos>` → `<PackageInfo>`

**Example:**

[source,xml]
----
<packageInfos>
  <PackageInfo packageName="uro">
    <ns>http://www.opengis.net/citygml/ext/uro/2.0</ns>
    <version>2.0</version>
  </PackageInfo>
</packageInfos>
----

**Fields:**

* `packageName`: UML package name
* `ns`: XML namespace for package
* `version`: Package version
* `xsdDocument` (optional): Output XSD filename

== Configuration file format (future)

Planned support for YAML configuration files.

**Example:** `~/.lutaml-klin/config.yaml`

[source,yaml]
----
defaults:
  verbose: true
  xsd_path: /path/to/default/schemas

generate:
  output_dir: mappings/

report:
  output_dir: reports/
  format: text

validate:
  strict: true
  check_multiplicities: true
----

NOTE: This feature is planned but not yet implemented.

== Best practices

=== Use absolute paths in scripts

[source,shell]
----
# Good
lutaml-klin generate \
  --xmi "$(pwd)/models/model.xmi" \
  --config "$(pwd)/config/config.xml" \
  --output "$(pwd)/output/mapping.yaml"

# Avoid (relative paths can be ambiguous)
lutaml-klin generate --xmi model.xmi --config config.xml --output map.yaml
----

=== Set environment variables in CI/CD

[source,shell]
----
# In .gitlab-ci.yml or similar
variables:
  LUTAML_KLIN_VERBOSE: "1"
  LUTAML_KLIN_LOG_LEVEL: "debug"
----

=== Organize configuration files

[source]
----
project/
├── config/
│   ├── shapechange/
│   │   ├── base-config.xml
│   │   ├── uro-config.xml
│   │   └── bldg-config.xml
│   └── namespaces/
│       ├── StandardNamespaces.xml
│       └── StandardMapEntries.xml
----

=== Document custom type mappings

When adding custom type mappings to ShapeChange config, document them:

[source,xml]
----
<!-- Custom type mapping for project-specific type -->
<XsdMapEntry>
  <type>CustomIdentifier</type>
  <xmlType>string</xmlType>
  <xmlTypeNs>http://www.w3.org/2001/XMLSchema</xmlTypeNs>
  <!-- Pattern: [A-Z]{2}[0-9]{6} -->
</XsdMapEntry>
----

== Common configurations

=== Minimal configuration

Simplest working configuration:

[source,shell]
----
lutaml-klin generate \
  --xmi model.xmi \
  --config config.xml \
  --output output.yaml
----

=== Standard PLATEAU configuration

For PLATEAU urban planning data:

[source,shell]
----
lutaml-klin generate \
  --xmi plateau-uro.xmi \
  --config ShapeChangeConfig_Plateau_urf.xml \
  --output mappings/uro.yaml \
  --verbose
----

=== Multi-package processing

Process and merge multiple packages:

[source,shell]
----
# Generate individual mappings
for pkg in uro bldg tran; do
  lutaml-klin generate \
    --xmi ${pkg}.xmi \
    --config ${pkg}-config.xml \
    --output mappings/${pkg}.yaml
done

# Merge
lutaml-klin merge \
  --inputs mappings/uro.yaml,mappings/bldg.yaml,mappings/tran.yaml \
  --output mappings/complete.yaml
----

=== Full workflow with validation

Complete end-to-end processing:

[source,shell]
----
# 1. Generate mapping
lutaml-klin generate \
  --xmi model.xmi \
  --config config.xml \
  --output mapping.yaml \
  --verbose

# 2. Generate report
lutaml-klin report \
  --mapping mapping.yaml \
  --output report.txt

# 3. Validate
lutaml-klin validate \
  --mapping mapping.yaml \
  --xsd schemas/ \
  --verbose
----
