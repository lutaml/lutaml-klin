= Rule: rule-xsd-cls-no-abstract-classes

== Overview

Do not convert abstract classes to object elements and do not process their properties; create a property type with references to subtypes with object elements instead.

== Priority

Should-have (used for abstract type handling)

== ShapeChange Documentation

Source:: `/Users/mulgogi/src/external/ShapeChange/shapechange-app/src/docs/asciidoc/targets/xml schema/Non_Standard_Conversion_Rules.adoc` (lines 527-532)

Description::
Abstract classes are not encoded as concrete types in XSD. Instead, properties that reference abstract classes are encoded with a choice of concrete subtype elements.

== Java Implementation

Source:: [`XsdDocument.java:pComplexType`](lines 1159-1174) and [`XsdDocument.java:mapPropertyType`](lines 3159-3162)

=== Algorithm

The Java implementation follows this process:

==== For Class Processing (pComplexType):

. Check if class is abstract
. Check if class matches [`rule-xsd-cls-no-abstract-classes`]
. If both conditions met: Treat like MIXIN class
. Do not create object element for the abstract class
. Do not create regular complex type

==== For Property Processing (mapPropertyType):

. Check if property value type is abstract
. Check if value type matches [`rule-xsd-cls-no-abstract-classes`]
. Create anonymous property type with choice of subtypes
. Find all concrete subtypes using [`subtypes()`] method
. Add element references for each concrete subtype

==== For Subtype Discovery (subtypes):

. Recursively walk down subtype tree
. For each subtype:
  * If it's a MIXIN: Continue recursion
  * If it's abstract and matches this rule: Continue recursion
  * Otherwise: Add to result set (it's instantiable)

// In pComplexType - treat abstract classes like mixins
private HashSet<ClassInfo> subtypes(ClassInfo ci) {
    HashSet<ClassInfo> res = new HashSet<ClassInfo>();
    if (ci.subtypes() != null) {
        for (String subtypeId : ci.subtypes()) {
            ClassInfo cix = model.classById(subtypeId);
            if (cix != null && (cix.category() == Options.MIXIN ||
                (cix.matches("rule-xsd-cls-no-abstract-classes") &&
                 cix.isAbstract()))) {
                res.addAll(subtypes(cix));
            } else {
                res.add(cix);
            }
        }
    }
    return res;
}

=== Design Principles

. Abstract classes are not instantiable in XSD
. Properties reference concrete subtypes via choice
. Recursive subtype discovery handles nested abstractions
. Treats abstract classes similar to mixins

=== Implementation Details

The [`NoAbstractClassesProcessor`] class extends [`BaseRuleProcessor`] and:

. Detects abstract classes that match the rule
. Prevents object element creation for abstract classes
. Creates choice-based property types for properties with abstract value types
. Recursively finds all concrete (instantiable) subtypes
. Generates element references for each concrete subtype

=== Test Case 1: Abstract class with concrete subtypes

Input UML::
[source]
----
abstract class AbstractFeature
  property id: String [1]

class Building extends AbstractFeature
  property floors: Integer [1]

class Road extends AbstractFeature
  property lanes: Integer [1]

class City
  property features: AbstractFeature [0..*]
----

Expected XSD::
[source,xml]
----
<!-- No element or type for AbstractFeature itself -->

<complexType name="BuildingType">
  <complexContent>
    <extension base="...">
      ...
    </extension>
  </complexContent>
</complexType>

<element name="Building" type="BuildingType"/>

<complexType name="RoadType">
  <complexContent>
    <extension base="...">
      ...
    </extension>
  </complexContent>
</complexType>

<element name="Road" type="RoadType"/>

<!-- Property with abstract type uses choice -->
<element name="features" minOccurs="0" maxOccurs="unbounded">
  <complexType>
    <choice>
      <element ref="Building"/>
      <element ref="Road"/>
    </choice>
  </complexType>
</element>
----
